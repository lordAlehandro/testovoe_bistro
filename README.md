# Картотека граждан — компактная версия

Учёт граждан: дашборд с показателями и графиками и картотека на 100 000 записей с поиском,
фильтрами и карточкой человека. Карточка разбита на разделы: основные сведения, документы,
адреса, контакты, семья, образование. Есть светлая и тёмная тема.

## Запуск

Нужен Docker.

```bash
docker compose up --build
```

Откройте http://localhost:8081. При первом запуске база сама создаёт схему и заполняется
100 000 тестовых граждан, это занимает около 30 секунд.

Чтобы начать с чистой базы: `docker compose down -v && docker compose up --build`.

### Режим разработки

База поднимается в Docker, сервер и фронт запускаются локально:

```bash
docker compose up -d db                 # PostgreSQL на localhost:5433
cd server && npm i && npm run dev       # API на localhost:3000
cd web && npm i && npm run dev          # фронт на localhost:5173, /api проксируется на сервер
```

Проверка типов: `npm run typecheck` в `server` и `web`.

## Устройство

```
server/
  db/01_schema.sql   схема: citizen + 5 таблиц разделов, ограничения, индексы
  db/02_seed.sql     генерация 100 000 граждан прямо в PostgreSQL
  src/citizens.ts    список с фильтрами, карточка, создание и правка гражданина, записи разделов
  src/dashboard.ts   все цифры дашборда
  src/index.ts       Express и единый формат ошибок
web/src/
  card.ts            описание всех полей и разделов карточки
  dicts.ts           справочники: коды хранятся в БД, подписи живут на фронте
  lib/               API (TanStack Query), валидация, маски, форматирование
  components/        поля формы, разделы-таблицы, карточка
  pages/             дашборд, картотека, мастер создания
```

Главные решения:
- **Карточка строится по описанию.** Форма, просмотр, проверка и мастер берут поля из `card.ts`.
  Поэтому 150 параметров не означают 150 кусков вёрстки.
- **Проверка в двух местах.** Фронт проверяет поля сразу при вводе. Окончательную проверку делает
  PostgreSQL через NOT NULL, CHECK и UNIQUE; если запрос пришёл в обход формы, сервер отвечает понятным текстом.
- **Сервер пишет только перечисленные колонки** (`COLUMNS` в `citizens.ts`). Лишние и системные поля
  из запроса (`id`, `created_at`) отбрасываются.
- **Zod** проверяет параметры списка: неверная сортировка или размер страницы дают 400, а не ошибку SQL.

## Что стоило бы добавить, будь больше времени

Для работы с реальными данными:
- Вход в систему, роли и права доступа. Сейчас чувствительные данные (СНИЛС) только маскируются,
  а нужно ещё ограничивать, кто их видит и меняет.
- Журнал изменений карточки: кто, когда и что поменял.
- Защиту от одновременной правки одной карточки двумя людьми (оптимистичная блокировка по версии записи).
- Автотесты: правила формы и проверки СНИЛС/ИНН на фронте, запросы списка и записи на сервере.

Для удобства:
- Удаление гражданина и записей разделов, правку записей разделов (сейчас их можно только добавлять).
- Ошибки сервера у конкретного поля, а не общим сообщением над формой.
- Фильтры в адресе страницы, чтобы выборкой можно было поделиться ссылкой (сейчас в адресе только `?id=` карточки).
- Мобильную вёрстку.
- Обновления в реальном времени (WebSocket) и раздел обращений граждан.

Для роста:
- Описание полей с сервера, а не из сборки фронта: новое поле появлялось бы без пересборки.
- Keyset-пагинацию вместо OFFSET: сейчас дальние страницы открываются медленнее (около 0,3 с на
  странице 4000), а на миллионах записей разница станет заметной.
- Разделение сервера на сервисы (картотека, справочники, аналитика), когда вырастет нагрузка и команда.
